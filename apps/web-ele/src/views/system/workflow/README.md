# 配置流程：设计、发布与办理

第二阶段提供可运行的 Mock 闭环：发布版本 → 选择已有协议发起 → 我的待办 → 填报节点嵌完整协议 → 保存/提交回写整单 → 审批只读、可撤回/会签/转办 → 抄送知会 → 并行分叉汇聚 / 子流程 → 修改重提 → 条件分流 → 结束。管理员可在流程监控换人/挂起/终止/催办。节点可配自然小时时限，到达/超时等写入站内信。入口为“系统管理 → 流程设计 / 流程监控”和侧栏“流程办理”。协议详情工具栏“发起配置流程”会锁定当前协议。流转失败时协议不落盘。

## 五分钟测试

1. 使用具备流程设计权限的账号登录。菜单没有出现时重新登录。角色管理可单独勾选「流程设计」「流程办理」及按钮（新建/发布/发起等）：管理员默认可设计+办理+发起；录入岗默认可发起和办理；律师审核岗默认可办理、不可发起。
2. 新建流程：名称“协议审核演示”，编码 `FL_XY_DEMO`，基地 `JD_TEST`，业务表 `XieYi`。
3. 进入设计器，点击“载入审核示例”。依次选中“科长审核”“分管领导核准”“签订确认”，将办理人都设为“发起人本人”。这样一个账号即可测试全部环节；实际业务可改成不同用户或角色。
4. 暂不绑定页面或表单，使用默认协议资料。保留示例中的通过/驳回连线和按钮，点击“保存草稿”，再点击“发布”，通过检查后确认发布。
5. 打开“流程办理 → 发起流程”，选择刚发布的流程，再选择一条已有协议（如 `LL-4-015`）。确认后办理资料来自该协议，不再手填迷你表单。
6. 打开待办后，“办理资料”直接展示该协议的基础信息与房屋/补偿/奖励/人口。在“经办人填报”修改房屋坐落或补偿项目，点击“保存”，办理页与“打开协议详情”应同时看到回写结果，然后“提交”。当前节点变为“科长审核”，协议正文只读，可填意见后通过或驳回。
7. 点击“驳回”，选择“经办人填报”，填写“请补充地址”。退回后修改资料并提交，回到科长。科长通过后，金额判断自动进入“分管领导核准”。
8. 领导通过 → 预签约提交 → 签订确认通过，流程结束。“我发起的”“我的已办”中可查看结束状态、流程图和审批记录。
9. 另选金额低于 100 万的协议（或把该协议金额改小后发起）；科长通过后应直接进入预签约，跳过领导。
10. 可另开两个窗口办理同一个任务：第一个成功后，第二个旧任务操作应提示版本变化并要求刷新。列表中“新建版本”可创建 V2，发布后新实例使用 V2，已有 V1 实例仍按 V1 办理。停用只禁止新发起。
11. 撤回：在“经办人填报”打开「允许撤回」后发布新版本。提交到科长后，发起人打开该单应看到「撤回至经办人填报」；科长未办理前可撤回。科长保存或通过后撤回按钮应变灰。
12. 会签：将“科长审核”办理方式改为「会签（全部通过）」，候选角色下至少两名办理人。提交后两人各自待办；一人通过仍停在科长，另一人通过才流转；任一人驳回则另一人待办作废。
13. 法务复核：在审批节点字段权限中选择「法务意见」并设为可编辑，发布新版本。提交到该节点后协议正文仍只读，可填写法务意见后通过；该意见写入协议 `flowFields`。驳回再进入该节点时仍可编辑原值，后续节点只读回看「已填流程字段」。
14. 菜单/按钮：系统管理 → 角色管理 → 按钮页可见「新建流程」「发起流程」等。去掉某角色的「发起流程」后，该账号流程办理页不再显示发起按钮，协议详情也不再显示「发起配置流程」；直接调发起接口会 403。
15. 流程监控：管理员打开「系统管理 → 流程监控」，应看到全部在途/已结束实例及当前待办人。点「查看」进入办理页只读检查（非候选人不能通过/提交）。点「干预」可换人、挂起、激活、终止（必填原因）或催办，审批记录会留下对应动作。挂起后原待办人列表不再显示该单，激活后恢复。录入岗、律师岗没有该菜单。
16. 抄送：在填报与科长之间拖入「抄送」节点，指定人员或角色，只画通过连线、不要配置按钮。发布后提交填报，流程应直接到达科长；被抄送人「我的待办」为空，可在「抄送给我」查看（只读）。抄送人无效时提交回滚，协议不落盘。
17. 并行：拖两个「并行网关」。第一个画出两条通过连线到两个审批（分叉），第二个收集两路后再连到下一节点（汇聚）。提交填报后两人同时有待办；都通过后才汇聚。一路驳回会作废另一路待办。
18. 子流程：先发布一条简单流程。在主流程中拖入「子流程」节点，选择刚发布的流程。主流程到达该节点后会出现子流程待办；子流程结束后主流程沿通过连线继续。不能绑定自身。
19. 转办：在填报或审批节点打开「允许转办」后发布。当前办理人点「转办」，选择其他有流程办理权限的人。转办后自己进入已办，对方成为新待办人；未保存的协议修改不会带给对方。下一节点若已被转办，上一环节撤回应变灰。若同时打开「转办后转回」，对方提交或通过后待办回到转办人，由转办人再办理；对方驳回仍按驳回路径退回。
20. 监控干预：管理员在监控页对办理中的单点「干预」：换人改派当前待办；挂起后办理按钮不可用；激活恢复；催办在列表打标并写记录；终止必填原因并作废待办。未做任意跳转节点。
21. 时限与通知：在填报/审批节点配置办理时限（自然小时，24=1 天）和临期提醒。待办列表显示剩余时限，可筛即将到期/已超时。任务到达、抄送、催办、驳回、结束、终止、临期、超时会写入站内信，顶栏通知可点进办理页。超时默认只提醒，可选「催办」；不会自动通过。挂起期间暂停计时。
22. 部门负责人：将“科长审核”办理人策略改为「指定部门负责人」，勾选「研发中心」（或未单独配负责人的「前端组」，会沿上级解析到研发中心）。发布后由录入员提交，待办应落到研发中心负责人（演示账号 `entry`，用户 ID `3`）。总公司负责人为管理员（ID `1`）。停用部门不能作为候选。
23. 数据动作：点中填报或审批节点，在右侧「数据动作」添加规则。例如填报「到达节点」把受理意见写成「待填报」，「提交时」把房屋坐落抄到协议备注；科长「到达节点」把法务意见写成「待审核」，「通过时」再改成「已通过」。不支持公式。动作失败则本次保存/提交整单回滚。
24. 依次审批：将“科长审核”办理方式改为「依次审批」，办理人用指定人员勾选两人（顺序即办理顺序）。提交后只有第一人有待办；通过后第二人才出现。任一人驳回则退回，后面的人不会出待办。
25. JSON 导入导出：设计器左侧「导出 JSON」下载设计文件；草稿可「导入 JSON」替换画布（名称/编码/基地不变）。列表页也可导入新建（需另填唯一编码）或对某行点「导出」。
26. 比例会签：将“科长审核”办理方式改为「比例会签」，通过百分比填 50，候选角色下至少两名办理人。提交后两人各自待办；一人通过即进入下一节点，另一人待办作废。若百分比为 100，则须两人都通过。任一人驳回则整单退回。转办只替换办理人，不增加会签人数。
27. 版本差异：先发布一版，再「新建版本」改节点名、办理人或办理方式后保存。回到列表点「对比」，选择另一版本。应看到改名、办理人、办理方式、新增或删除的节点和连线。对比只读，在途实例仍走原版本。
28. 流程图打印：设计器右上角「打印」按整张图输出（不受当前缩放影响），驳回线为红色虚线。办理页「流程图」页签也可打印，绿色为已到达、蓝色为当前节点。打印不修改流程。
29. 转办转回：在填报节点同时打开「允许转办」和「转办后转回」后发布。经办人把待办转给另一人。对方提交后流程仍停在填报，待办回到经办人；经办人再提交一次才进入下一节点。对方若把待办直接转回经办人，经办人提交一次即可离开。对方若驳回（审批节点），则按驳回路径退回，不会转回。
30. 表单字段取人：将“科长审核”办理人策略改为「表单字段取人」，人员字段选「经办人」。给协议基本信息写入经办人用户 ID 后发起。填报提交后，待办应落到该用户，而不是角色里的其他人。字段为空、或该用户没有流程办理权限时，提交回滚，协议不落盘。协办人字段同样可用，多人用逗号或顿号分隔。
31. 配置变更日志：新建版本后，改某一节点的按钮、办理时限、数据动作或字段权限，保存再发布。列表点「对比」，下方应出现该版本的日志：操作人、时间，以及「保存」「发布」两条。只改节点名称不会写入这条日志。日志只读，已发起的实例仍走原版本。

多账号测试：将三个审批节点绑定不同用户/角色。待办只对候选人显示。审批节点默认为任一人办理，会签需显式选择「全部通过」，依次审批按名单顺序一人办完才轮到下一人。比例会签按百分比向上取整，达到人数即流转并作废其余待办。发起人和已参与人可以查看，具有流程监控或流程管理权限的管理员可检查全部实例；管理员仍须成为候选人才能办理。抄送人不进入待办。并行两路各自待办，汇聚前监控页当前节点会同时显示两路名称。

## 设计器

- 从左侧添加节点，拖动节点调整位置；拖动画布平移、滚轮缩放。抄送节点只配置抄送人，不绑定表单和按钮。并行网关成对使用（分叉 / 汇聚）。子流程节点选择已发布流程。填报/审批可打开「允许撤回」「允许转办」，转办可再开「转办后转回」（对方提交或通过后回到转办人），并配置办理时限和数据动作。审批办理方式可选任一人、会签、依次或比例（达到百分比，人数向上取整）。「指定部门负责人」勾选部门，运行时按组织树取负责人（未配则沿上级上溯）。「表单字段取人」选择经办人或协办人，运行时按协议上的用户 ID 分派。可导出/导入流程 JSON。
- 从节点右侧圆点拖到目标节点，或点圆点后点击目标节点，生成连线。点击连线设置通过、驳回、条件及“否则”出口。
- 驳回线从审批节点指向上游人工节点。运行时仅允许退回实际办理过且符合“驳回范围”的节点；驳回意见必填。
- “回到驳回节点”使退回节点重提后直接回到驳回方；“从退回节点重新流转”沿退回节点的正常出口重新判断。
- 草稿支持撤销/重做、Ctrl+S 保存、Delete 删除、退出未保存提醒；不完整的图可保存，但不能发布。
- 发布快照只读，修改须新建版本。列表「对比」可查看两个版本的节点、连线、办理人、办理方式，以及按钮、时限、数据动作和字段权限差异。较新版本下方有配置变更日志，记下保存或发布时的操作人和时间。表单字段配置随发布冻结，修改模板不会改变已发布流程。

## 表单、权限与发布检查

办理页在绑定协议后嵌入协议模块，不再只展示四个头字段。头字段仍用于条件分流：`agreementNo`（只读）、`compensatee`、`houseAddress`、`BuChangJinE`（非负数）。填报节点默认可改协议正文，审批节点默认整单只读。节点「字段权限」可从目录选择协议头字段或节点字段（如法务意见）；审批节点把某字段设为可编辑后，办理页出现「本节点字段」并可回写到协议 `flowFields`。只读/隐藏字段由服务端还原。未绑定协议的实例仍回退到冻结表单。

静态 FormCreate 模板支持 input、textarea、inputNumber/number、datePicker（日期/日期时间）、select/radio（单选静态选项）、switch、tableForm。支持必填、数字范围、文本长度和明细行数校验。服务端再次验证值、候选身份、按钮、任务版本和字段权限；隐藏字段的值不返回客户端。表格包含隐藏/只读列时，整张表暂为只读。

页面绑定仅支持通过 fcBindings/fcRules 提供的静态详情字段；模块权限、页面与列模板字段权限共同生效。带独立 moduleInner 配置的页面、脚本联动、动态选项、任意自定义校验、多选/范围等未适配配置会在发布时明确阻止，请改绑受支持的静态模板。当前不完整复现旧协议页面的专用模块布局和操作。

条件在服务端解析，支持数字、字符串、布尔值、字段、`> >= < <= == !=`、`&& || !`、括号。例如 `BuChangJinE >= 1000000`。禁止脚本、函数和赋值；字段必须存在于发布表单中。运行时缺值、比较类型错误、多个条件同时命中，都会回滚本次提交；未命中时走“否则”。所有条件操作数均会检查，不提供 JavaScript 短路求值语义。

发布检查还会验证图结构、办理人有效性、角色中是否存在可办理的人员、部门负责人是否可解析到具备办理权限的用户、数据动作字段与时机、必要动作和绑定资源。当前支持业务表 `XieYi`、保存/提交/通过/驳回/撤回/转办（可配置转办后转回）、审批会签、依次审批、比例会签、抄送知会、并行分叉汇聚、同基地子流程、指定部门负责人、表单字段取人、到达/按钮数据动作（赋值或抄字段）、流程 JSON 导入导出、流程图打印，以及自然小时时限/站内通知。旧协议自定义动作、完整公式引擎、工作日历与自动通过尚未接入。

## 接口与数据

| 方法 | 路径（统一 `/api` 前缀） | 用途 |
| --- | --- | --- |
| GET / POST | `/system/workflow/list` / `/system/workflow` | 查询版本 / 创建草稿 |
| GET / PUT / DELETE | `/system/workflow/:id` | 获取 / 更新 / 删除草稿 |
| GET | `/system/workflow/options` | 角色、用户、部门、页面/表单、已发布流程（子流程绑定） |
| GET | `/system/workflow/:id/check` | 发布检查 |
| POST | `/system/workflow/:id/publish` | 按 revision 发布并冻结表单 |
| POST | `/system/workflow/:id/version` | 从历史版本创建新草稿 |
| POST | `/system/workflow/:id/disable` | 停用版本 |
| GET | `/workflow/definitions` | 可发起的已发布版本 |
| GET | `/workflow/agreements` | 可绑定的已有协议 |
| GET / POST | `/workflow/instances` | 查询 todo/done/started/cc/monitor / 按协议编号发起实例 |
| GET | `/workflow/instances/:id` | 实例、当前表单、动作、图和记录 |
| POST | `/workflow/instances/:id/action` | 保存、提交、通过、驳回、撤回或转办 |
| POST | `/workflow/instances/:id/intervene` | 监控换人、挂起、激活、终止、催办 |
| GET | `/workflow/notices` | 当前用户流程站内通知 |
| POST | `/workflow/notices/read` | 标记已读（可指定 id） |

设计接口要求 `System:Workflow:Manage`，办理接口要求 `Workflow:Use`（或 `Workflow:Start`），发起实例额外要求 `Workflow:Start`，监控全量列表与干预要求 `Workflow:Monitor` 或管理权限。具备 `System:Workflow:Manage` 的账号可同时设计、发起、办理和监控。实例访问仍检查办理范围（监控权限可看全部实例）。发起/办理/干预提供 requestId 幂等控制；办理还要求 taskId 和 revision，版本过期返回 409。不能通过浏览器提供下一节点改变流转结果。

`apps/shared/workflow.ts` 为设计契约；`workflow-runtime.ts` 为运行契约；`workflow-expression.ts` 为条件解析。Mock 的 workflow-store、workflow-publication、workflow-forms、workflow-engine 分别负责版本存储、发布检查、表单快照和任务流转。数据在 Nitro 的 DATA_DIR 下保存为 `workflow.json`、`workflow-instances.json`，后者将任务、数据、事件和幂等记录一起原子写入。该文件存储适用于单进程本地演示；生产应替换为事务数据库、正式组织权限和业务数据接口。
